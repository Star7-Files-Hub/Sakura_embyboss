# 同时播放限制检测

## 功能概述

同时播放限制检测功能可以监控 Emby 服务器上所有用户的活跃播放会话，当某个用户的播放流数量超过**其适用的上限**（见下文「判定规则」）时，自动执行警告、终止所有流、群内通报，并在超过警告次数后自动封禁账号。

## 功能特性

- **播放限制**：设置每个用户允许的同时播放流数量（默认 2 个）
- **白名单独立上限**：白名单用户（`lv: a`）默认豁免，可在控制面板打开开关后单独设限（默认 4 个）
- **管理员永久豁免**：bot 管理员始终不受并发限制，硬编码、没有开关
- **自动终止**：超限后强制终止该用户的所有播放流
- **私信警告**：向违规用户发送私信警告
- **群内通报**：违规事件自动发送到配置的主群
- **累计警告**：记录每个用户的警告次数
- **自动封禁**：超过警告阈值后自动封禁账号
- **灵活配置**：所有限制参数均可通过控制面板调整

## 配置说明

在 `config.json` 中添加以下配置项：

```json
{
  "concurrent_play_limit_enabled": false,
  "concurrent_play_limit": 2,
  "concurrent_play_warn_threshold": 3,
  "concurrent_play_check_interval": 60,
  "concurrent_play_limit_whitelist_enabled": false,
  "concurrent_play_limit_whitelist": 4
}
```

| 配置项 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `concurrent_play_limit_enabled` | bool | `false` | 是否启用同时播放限制检测 |
| `concurrent_play_limit` | int | `2` | 每人允许的同时播放流数量 |
| `concurrent_play_warn_threshold` | int | `3` | 警告次数上限，超过自动封禁 |
| `concurrent_play_check_interval` | int | `60` | 检测间隔（秒），建议 30-300（面板最小 10） |
| `concurrent_play_limit_whitelist_enabled` | bool | `false` | 白名单用户是否也纳入并发限制；`false` = 白名单豁免 |
| `concurrent_play_limit_whitelist` | int | `4` | 白名单用户适用的上限，仅在上项为 `true` 时生效（面板输入范围 1-99） |

## 判定规则

检测到某个 Emby 账号的播放流数量后，先按 Emby UserId 到 bot 数据库里查用户记录（查不到的直接按第 2 条处理），再按下面的优先级判定（与代码实现一致，从高到低）：

1. **bot 管理员 → 永久豁免**：账号的 Telegram ID 在 bot 管理员列表里就一律跳过检查。这是**硬编码**的豁免，**没有开关**可以改，避免管理员把自己锁死；即使该账号同时还是白名单，也照样豁免。
2. **不在 bot 数据库里的 Emby 账号 → 跳过并记 warning**：例如直接建在 Emby 侧、bot 里没有记录的账号，既无法私信告警也无法封禁，因此会被跳过（日志里记一条 `WARNING`，含 Emby UserId 与 UserName）。**这类账号等于永久不受并发限制**，建议为其在 bot 中建档。
3. **白名单（`lv: a`）**：
   - `concurrent_play_limit_whitelist_enabled = false`（默认）→ 豁免，不做限制；
   - `= true` → 按 `concurrent_play_limit_whitelist`（默认 4）这个独立上限判定。
4. **其他用户** → 按 `concurrent_play_limit`（默认 2）判定。

判定用的是「该用户适用的上限」：播放流数量**严格大于**适用上限才会被终止 + 警告（正好等于上限不算超限）。群内通报和私信里显示的「限制: N 个」就是这名用户适用的上限（白名单用户显示的是白名单上限）。

> 📌 检测循环里会先用「可能生效的上限中较小的那个」做粗筛（开启白名单受限时即 `min(普通上限, 白名单上限)`），明显没超限的用户不查库就直接跳过；这只是性能优化，不会漏判。

**举例**（默认配置：普通上限 2、白名单上限 4、白名单受限关闭）：

| 账号类型 | 播 2 个流 | 播 3 个流 | 播 5 个流 |
|---|---|---|---|
| bot 管理员 | 不受限 | 不受限 | 不受限 |
| 白名单 `lv: a` | 不受限 | 不受限 | 不受限 |
| 普通用户 | 正常 | ⚠️ 终止 + 警告 | ⚠️ 终止 + 警告 |
| 不在 bot 数据库 | 不受限（仅记 warning） | 不受限（仅记 warning） | 不受限（仅记 warning） |

把「白名单是否受限」打开、白名单上限设为 4 之后，白名单账号播 5 个流同样会被终止 + 警告，播 2/3 个流仍然正常。

## 控制面板操作

在 bot 中输入 `/config` 打开控制面板，找到 **🎬 同时播放限制** 进入设置子面板。子面板顶部会显示当前状态、播放限制、白名单受限与白名单上限、警告阈值、检测间隔，并列出判定顺序。

### 设置选项

- **开关同时播放限制**：启用/禁用功能。按钮随状态显示 `❎ 同时播放限制`（未开启）、`✅ 同时播放限制`（已开启且定时任务在跑）或 `⚠️ 同时播放限制(未生效)`（开关已开但检测任务未注册，关闭再开启一次开关即可恢复）
- **设置播放限制数**：每人允许的同时播放流数量（默认 2，需输入大于 0 的整数）
- **白名单是否受限**：`❎`（默认）时白名单豁免；点成 `✅` 后白名单按白名单上限判定
- **设置白名单上限**：白名单用户允许的同时播放流数量（默认 4，面板接受 1-99）
- **设置警告阈值**：超过此次数将自动封禁
- **设置检测间隔**：检测周期（秒，面板最小 10，建议 30-300）
- **重置所有警告计数**：一键清零所有用户的警告记录

### 单个用户的警告调整

「重置所有警告计数」是整体操作。如果只是某个用户被误判、或者你想对他网开一面，用 `/kk` 单用户面板处理：

```
/kk [tg_id]        # 或对某人回复 /kk
```

面板里会多出一行 **`· ⚠️ 并发警告 | N / 阈值 次`**，以及三个按钮：

- **➕ 警告+1**：把该用户的警告计数加 1。达到或超过阈值时会额外提示「已达/超过阈值 N，如需封禁请点『💢 禁用账户』」——**手动调整不会自动封禁**，封禁始终是独立动作
- **➖ 警告-1**：把该用户的警告计数减 1。已经是 0 时不会变成负数，只提示「当前警告数已经是 0，无需再减」
- **🔄 重置警告**：把该用户的警告计数清零

按钮布局按**语义**分组，而不是按功能域：

```
[💢 禁用账户]        [⚠️ 删除账户]
[关闭 额外媒体库]    [🔄 重置警告]      ← 两者都是「把某个开关切到某个状态」
[➕ 警告+1]          [➖ 警告-1]        ← 两者都是「在当前值上增减」
[🚫 踢出并封禁]      [❌ 删除消息]
```

「关闭/开启 额外媒体库」按钮是**有条件显示**的（`extra_emby_libs` 未配置、或 Emby
查询失败时都不出现）。它不存在时，**「🔄 重置警告」单独占一行** —— 位置稳定，
不会因为一个按钮的消失而挤进 `+1/-1` 那一行。

警告按钮刻意不参与按钮分块（`array_chunk`），避免被「额外媒体库」按钮的奇偶
影响而拆散错位。读取计数失败时面板显示「读取失败」而不是假装是 0。

三个操作都只改数据库里的 `concurrent_warn_count` 一个字段 —— **不会解除封禁、不会改动 Emby 策略、不会影响其他用户**。点完后面板会立即重渲染，计数当场更新。

> **计数不会丢失更新**：并发检测任务同样会写这个计数，而它在写入前要执行一段
> 秒级的「终止播放流」I/O。若沿用 I/O **之前**读到的值做绝对写入，就会出现：
> 任务读到 5 → 管理员点「🔄 重置警告」清零 → 任务回来写 6，**重置被静默抹掉**；
> 更糟的是 6 若达到阈值，同一流程会紧接着自动封禁 —— 管理员刚重置完，用户反而被封。
> 因此检测任务把「读计数」挪到**写之前**，且读与写之间没有 `await`
> （asyncio 协作式调度，这一段对事件循环是原子的）；管理员侧同理。
> 回归测试：`tests/test_warn_count_race.py`（用 mock 让 I/O 在飞行中真的改一次库）。

> 面板刷新不会静默失败：
>
> 1. 重渲染用的是「刚写入的那个值」，而不是再查一次库 —— 渲染结果与写入动作严格对应。
> 2. 面板文本只反映**上一次渲染时**的计数。并发检测在别处把计数 +1 时，已打开的面板
>    就会停在旧值；这时管理员点「➖ 警告-1」，写回的值可能正好等于面板上已经显示的值，
>    Telegram 会以 `MESSAGE_NOT_MODIFIED` 拒掉编辑 —— 看起来就是「操作成功了但数字没动」。
>    因此并发检测写完计数后会立刻回调 `sync_kk_panel()` 把已打开的面板刷成最新值。
> 3. 同一个「管理员 + 被查看用户」只保留最新一条面板：发新面板前会删掉上一条，
>    避免管理员对着一条陈旧面板操作。
> 4. 万一消息真的编辑不了（例如被删除），会自动改发一条新面板并删掉旧的；
>    连改发都失败时会给管理员弹一个 `show_alert` 告警，而不是让他以为一切正常。
> 5. 编辑被限流（`FloodWait`）会自动等待重试，重试期间不会误发新面板。
> 6. 回调**只会被答复一次**：先答「成功」、失败后再补一条告警是无效设计
>    （第二条会被 Telegram 以 `QUERY_ID_INVALID` 拒绝）。所以顺序是「先刷新、再应答」。
> 7. 极端情况下 `call.message` 为空（内联消息里的按钮）时，会明确返回刷新失败并
>    弹出告警，而不是抛异常 —— 抛出去会连答复都执行不到，回调在 Telegram 侧一直转圈。
>
> 具体错误码、消息 id、会话 id 都会写进日志。底层 `editMessage()` 里原先
> **完全静默**的三条 `BadRequest` 分支（`BUTTON_URL_INVALID` /
> `MESSAGE_NOT_MODIFIED` / `MESSAGE_ID_INVALID`）现在也会记日志，全仓 200+
> 处调用一并受益。
>
> 计数读不出来时面板显示「读取失败」而不是 `0` —— 读失败和真实的 0 必须区分开，
> 否则管理员会以为这个人没问题。用自解释文案而不是 `?`，是因为这一行普通用户
> 在 `/myinfo` 里也会看到。

未注册 Emby 账户的 TG 用户不显示这两个按钮（没有计数可调）。

> 注意：如果用户已经因为警告超阈值被封禁，调整警告数**不会自动解封**。解封请用同一个 `/kk` 面板上的「🌟 解除禁用」。

## 工作流程

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 定时检测（按设定间隔）                                      │
│    ↓                                                        │
│ 2. 获取 /emby/Sessions，按 UserId 分组                        │
│    ↓                                                        │
│ 3. 检查每个用户的播放流数量                                     │
│    ↓                                                        │
│ 4. 是否超过限制？                                              │
│    ├── 否 → 跳过                                              │
│    └── 是 → 继续                                              │
│         ↓                                                   │
│ 5. 礼貌性下发 Playing/Stop                                    │
│    （本服务器的客户端多不支持远程控制，通常无效，见下节）          │
│    ↓                                                        │
│ 6. 警告计数 +1，并刷新已打开的 /kk 面板                         │
│    ↓                                                        │
│ 7. 警告次数 ≥ 阈值？                                           │
│    ├── 是 → 封禁用户（禁用 Emby 账号，永久）                     │
│    └── 否 → 临时禁用账号 45 秒以**真正踢掉流**，到期自动还原       │
│    ↓                                                        │
│ 8. 私信警告用户 + 群内通报                                     │
│    ↓                                                        │
│ 9. 延迟复验（走踢流路径时等 60 秒，即**还原之后**）               │
│    把实测断开数量补发到群里，绝不当场宣称"已终止"                  │
└─────────────────────────────────────────────────────────────┘
```

图中的「是否超过限制」指该用户**适用的上限**：bot 管理员、以及默认配置下的白名单用户，在第 3 步就会被跳过；不在 bot 数据库里的账号也会被跳过并记 warning。详见上文「判定规则」。

## 终止流：为什么必须靠「临时封禁」

这是本功能最反直觉、也最容易改错的地方，改动前请先读完本节。

**结论：在这台 Emby 上，`POST /Sessions/{Id}/Playing/Stop` 对现有客户端群体 100% 无效；唯一真正能停流的手段是把用户策略的 `IsDisabled` 置真。**

`Playing/Stop` 并不是"服务端杀流"，它本质是**通过会话的远程控制通道向客户端下发一条 playstate 指令**。Emby 官方文档写明这类命令 "just assumed supported if `SupportsRemoteControl` is true"。2026-10-06 在 ChaPanda（Emby 4.10.0.40）上的实测：

| 证据 | 结果 |
|---|---|
| `/emby/Sessions` 里 `SupportsRemoteControl=True` 的会话 | **0 / 3643** |
| `GET /Sessions?ControllableByUserId=<userId>`（服务器自己算的"该用户可控的会话"） | 对 **admin、另一管理员、普通用户全部返回 0 条** |
| 对正在播放的会话调 `Playing/Stop` | HTTP **204**，但 +5s/+15s/+30s 复查**仍在播放** |
| `Playing/Pause` | 同样 204、同样无效（整条控制通道都是死的） |

其余候选机制也都实测排除：

| 机制 | 实测结果 |
|---|---|
| `DELETE /Sessions/{Id}` | 4.10 **没有这个路由**，返回 404 |
| `DELETE /Videos/ActiveEncodings` | 需要 `PlaySessionId`，而会话 DTO（`PlayerStateInfo` / `SessionInfo`）**根本没有这个字段**；且实测在播会话全是 DirectStream，无转码任务 |
| `DELETE /Devices?Id=` | 只吊销 token，**已建立的流会继续下载**；带保存密码的客户端会自动重登（实测两次结果相反），不可靠 |
| `SimultaneousStreamLimit` | **需要 Emby Premiere**（本站未开通）。实测设成 1 后第二条流照样能播，服务端完全不执行 |
| `EnableMediaPlayback=false` | 实测无效，流继续播 |

**唯一有效的是 `IsDisabled=true`**：禁用后 Emby **服务器自己**会把该用户的会话清成 0，且重新认证被拒（`403 您的账户已被禁用`）。实测停流窗口 **5~67 秒** —— 客户端要连续多次请求失败才放弃。

因此本功能第 7 步走的是「**临时封禁踢流**」：把账号临时禁用 `45` 秒，到期自动还原。账号并没有被封，用户无需重新登录（token 未被吊销），只是那几十秒播不了。

### 崩溃自恢复（重要）

「禁用」与「还原」之间隔着几十秒。进程若在这中间被 SIGKILL、容器被重建或机器断电，`try/finally` 与后台还原任务都不会执行，**用户会被永久锁死** —— 而他只会看到"看不了片"，根本不知道要找管理员。

所以到期时间落库在 `emby.kick_until`（`20260315_04` 迁移新增）：

1. **先落库、再禁用**。顺序不能反 —— 反过来的话「禁用成功、落库失败」就永久锁死了；现在这种顺序下最坏情况只是留下一条 `kick_until` 却从没禁用过，而还原它（写 `IsDisabled=false`）是无副作用的空操作。
2. **启动时无条件还原**所有 `kick_until` 非空的记录（`main.py` 的 `_on_startup`），不看是否到期 —— 宁可少踢一次流，也绝不能把用户锁在门外。
3. **周期巡检**兜底（每轮检测开头，只还原**已到期**的，避免打断进行中的踢流）。
4. **回读校验**：只有重新读到 `IsDisabled=False` 才清 `kick_until`；校验不过就**故意保留**标记让后续重试，并把问题喊到群里。
5. **还原失败的通报要节流**：还原失败会保留 `kick_until` 让周期巡检重试（每轮检测都会再试一次）。若不节流，一个策略永久读不到的账号会让群里**每 60 秒**刷一条同样的 🚨，很快被管理员无视、反而掩盖新问题。所以：同一用户 + **同一错误原因**在 `30` 分钟内只通报一次，**错误原因变了立刻通报**（那是新信息）；日志不受节流，每次失败都记 `ERROR`。
6. **还原成功后清掉节流记录**：节流是为了压制「**同一次**事故被反复重试」的刷屏，**不是**压制新事故。所以还原成功（回读确认为 `IsDisabled=False`）时会 `_clear_restore_alert()`。不清的话，同一用户**下一次**事故若原因恰好相同且落在 30 分钟窗口内，告警会被当成"重复"直接抑制 —— 群里一条 🚨 都没有，而用户是真的又被锁在门外了。
7. **节流 key 带 embyid**（`f"{tg_id}:{emby_user_id}"`）：`tg_id` 可能为 `None`（记录没关联 TG 用户），只用 `str(tg_id)` 会让所有无 tg 的记录挤进同一个 `"None"` 桶互相抑制。

### 三道防"误伤"护栏

共同目标只有一个：**绝不把管理员的封禁悄悄解开**。

1. **已被禁用的用户不踢**：若读到的 `IsDisabled` 本来就是 `true`（例如管理员刚手动封了他，而他的客户端还要几十秒才断流），检测任务**不会**把这次禁用当成"自己的临时封禁"，直接跳过。否则 45 秒后的还原会**把管理员的封禁悄悄解开**。
2. **接管护栏**：还原任务开工前先查 `kick_until`，若已被清空就**一次 Emby 调用都不发**直接返回。
3. **收口点统一清标记**：所有管理员/系统层面的显式策略写入（`emby_change_policy()`，覆盖全仓库 15+ 处封禁路径）成功后都会清掉 `kick_until`，声明"现在的禁用归本次调用负责"。详见下一节。

### 谁负责清 `kick_until`

`kick_until` 非空 = 「机器人为了踢流禁用了这个账号，到期要自己还原」。所以**任何一次管理员/系统层面的显式策略写入都必须先作废它**，否则会出现"管理员刚封的人，几十秒后被还原任务悄悄解开"。

全仓库有 15+ 处会把用户置为禁用（`/kk` 面板、`renew`、`syncs`、`create`、`userplays_rank`、`check_ex`、`user_info`、`ban_playlist`、`client_filter`、`line_report` …）。逐个调用点加清理**必然漏掉某个**，因此清理放在**唯一收口点** `emby_change_policy()` 里：只要 `POST /emby/Users/{Id}/Policy` 成功，就顺手把该用户的 `kick_until` 置空，表示"这次禁用归本次调用负责"。

两个例外，都是刻意的：

- **`set_user_disabled()` 不走这个收口点**。它必须能改写 `IsDisabled` 而不清掉自己刚落的标记 —— 否则「临时封禁踢流」当场就自我作废了。这也正是它和 `emby_change_policy()` 分成两个方法的原因之一。
- **`_restore_kick()` 也只用 `set_user_disabled()`**，所以还原动作不会误清自己的标记。

`disable=False`（解封）与 `admin=True`（提权，内部同样写 `IsDisabled=false`）同样会清 —— **管理员的手动操作永远优先于机器人的临时措施**。

## 群内通报格式示例

```
⚠️ 同时播放限制警告

用户: testuser (TG: 123456789)
Emby ID: abc123def456
当前播放流: 3 个 (限制: 2 个)
检测时间: 2024-01-15 14:30:25
累计警告: 2 / 3 次

  1. 🎬 电影A | 📱 Chrome
  2. 🎬 电影B | 📱 iPhone
  3. 🎬 剧集C | 📱 Android TV

📤 已下发停止指令: 3 个流（本服务器客户端多不支持远程控制，通常无效）

🦶 **已临时禁用该账号 45 秒以强制断流**（该客户端不支持远程停止指令，只能这样真正踢掉流），到期自动解封。
⚠️ 再犯 1 次将自动封禁账号！
```

走踢流路径时，`45 + 15 = 60` 秒后 bot 会再发一条**复验**通报，内容是实测结果。复验**先校验账号是否真的解封了，再谈流**：

```
🔎 踢流复验
用户: testuser
✅ 账号已解封，该用户**当前没有任何播放流**（原有 3 个已断开，未重连）。
```

若解封后他又连上了：

```
🔎 踢流复验
用户: testuser
⚠️ 账号已解封，但该用户**仍有 1 个流在播放**（原有 3 个）—— 很可能是解封后重连，请手动处理。
```

**为什么必须先校验账号状态** —— 这正是本项目最容易犯的"自报成功"：

`playing == 0` 有两种**完全不同的成因**：① 他确实没重连；② **他还被禁着，根本连不上**。如果 `_restore_kick` 到期还原失败（用户仍被禁用），复验只看到 0 个流就报"账号已解封、未重连"，群里会同时出现两条互相矛盾的消息：

```
🚨 临时封禁还原失败 … 该用户当前仍处于禁用状态
✅ 账号已解封，该用户当前没有任何播放流（未重连）
```

而后者是**假的**。所以复验在报流数之前先读一次 `IsDisabled`：

| 读到的状态 | 复验通报 |
|---|---|
| `False`（确实已解封） | 才进入上面两个分支，报流数 |
| `True`（还原失败） | 🚨 账号**仍处于禁用状态**（到期还原失败），该用户现在看不了片，请管理员手动解封 |
| 读不到 | ⚠️ 无法读取账号状态，**未能确认**是否已解封，请到 Emby 后台核对 |

**账号状态先查、流数后查，顺序不能反**：账号状态（`GET /emby/Users/{Id}`）与 `/emby/Sessions` 是**两个互相独立的接口**。若先查会话、而会话接口恰好挂了，代码只能返回一句「未能确认是否已停止」—— 于是一个"**用户被锁在门外**"的安全事故被掩盖成含糊话。先查状态，会话接口的故障就牵连不到它。状态为 `True`/`None` 时**根本不会去查会话**。

### 回退路径（没能踢流时）

踢流需要同时满足「知道 TG 用户」「能读到账号状态」「账号当前没被禁用」。任一不满足就走**回退路径**：只下发停止指令，然后按同样的口径复验。这条路径**同样优先按 UserId** 复验，因为按 session id 有致命盲点 —— 客户端重连拿到**新 id**，旧 id 从列表消失 → 报"已全部断开"，而真相是"他换了条新连接接着看"。

只有在**完全拿不到 `emby_user_id`** 时才退回 session id 口径，并且通报里会明确写出局限：

```
🔎 终止复验
用户: testuser
✅ 原会话已全部断开: 2/2 个。
⚠️ 本次只能按会话 ID 复验，**若他在此期间重连则会漏判**，请到 Emby 活动页核对。
```

> 复验的等待时间**必须晚于还原时刻**（所以是 60 秒而不是 30 秒）。否则是在"账号还禁着"的时候去复查，看到的"已断开"根本不能证明解封之后用户没有重新连上。

## 用户私信格式

```
🚫 播放限制警告

您的账号当前有 3 个播放流，超出限制 2 个。
已**临时禁用你的账号 45 秒**以强制断开播放（你的播放器不支持远程停止指令），到期会自动解封，无需联系管理员。
警告次数: 2 / 3

⚠️ 超过 3 次将自动封禁账号！
```

**私信文案按实际做了什么生成**，绝不出现"已终止"：

| 实际情况 | 文案 |
|---|---|
| 临时封禁踢流成功 | 已**临时禁用你的账号 N 秒**以强制断开播放（你的播放器不支持远程停止指令），到期会自动解封，无需联系管理员。 |
| 踢流失败 | ⚠️ **强制断流未能生效**，请**立即手动停止播放**，否则将直接封禁账号。 |
| 已达阈值被封禁 | 你的账号已被封禁。 |

## 数据库说明

警告计数存储在 `emby` 表的 `concurrent_warn_count` 字段；「临时封禁踢流」的还原到期时间存储在 `emby.kick_until`（`20260315_04` 迁移新增，`NULL` = 没有待还原的临时封禁）。

`kick_until` 非空表示"机器人为了踢流把这个账号禁用了，到期必须由机器人自己还原"。手工排查时如果发现有用户 `IsDisabled=true` 且 `kick_until` 非空，说明上次运行没正常收尾，重启 bot 即可自动还原（或直接手动解封）。

警告计数在用户被警告时自动递增，封禁后不会自动清零。

手动调整有两种粒度：

| 方式 | 作用范围 | 入口 |
|---|---|---|
| 重置所有警告计数 | 全部用户 | `/config` → 🎬 同时播放限制 |
| ➕ 警告+1 / ➖ 警告-1 / 🔄 重置警告 | 单个用户 | `/kk [tg_id]` |

单用户调整只写 `concurrent_warn_count` 这一个字段，不涉及封禁状态与 Emby 策略。

## 注意事项

1. **白名单默认豁免，但可以改成受限**：白名单用户（`lv: a`）默认不受并发限制；若希望白名单也守规矩，在控制面板打开「白名单是否受限」，再设置白名单上限（默认 4）。**bot 管理员是永久豁免的**，与这个开关无关。
2. **不在 bot 数据库里的 Emby 账号不受限**：这类账号（例如直接建在 Emby 侧）会被跳过并记一条 `WARNING`，既不会被告警也不会被封禁，建议为其在 bot 中建档以便统一管理。
3. **检测间隔不宜过短**：建议不低于 30 秒，避免对 Emby 服务器造成压力（面板最小 10 秒）
4. **与 Emby 原生限制的区别**：Emby 的 `SimultaneousStreamLimit` 策略会在播放开始时拒绝多余流，而本功能是在流已经开始后终止并警告。注意 `SimultaneousStreamLimit` **需要 Emby Premiere**，未开通时该字段不会被强制执行（实测设成 1 后第二条流照样能播）。
5. **`SupportsRemoteControl` 就是终止失败的原因**：本服务器上它 3643 个会话全为 `False`，`Playing/Stop` 因此是空操作。**不要**再根据"Stop 返回 204"判断终止成功 —— 204 只代表指令被受理。真正的判据只有两个：复验时 `/emby/Sessions` 里还有没有这个用户的流，以及 Emby 活动页的实际状态。
6. **踢流会把该用户当时所有流一起踢掉**，不只多出来的那条 —— 这是 `IsDisabled` 这个杠杆的固有代价，没有更细的粒度可用。

## 终止结果的处理（已下发 ≠ 已停止）

本功能**不会在当场就宣称"已终止"**，而是分三步如实告知：

1. **首报（立刻）**：只说指令下发的数量
   - `📤 已下发停止指令: N 个流（本服务器客户端多不支持远程控制，通常无效）`；
   - 有被服务端拒绝的，追加 ` | ❌ 服务端拒绝: N 个流`；
   - 并说明是否已做「临时封禁踢流」及其保持秒数。
2. **真正停流（立刻，与首报同轮）**：临时禁用账号 45 秒，到期自动还原。
3. **复验（60 秒后，即还原之后）**：先读一次账号 `IsDisabled`，再拉 `/emby/Sessions`，用**实测**结果补发一条群通报
   - 账号仍被禁用（还原失败）→ `🚨 账号仍处于禁用状态（到期还原失败），请管理员手动解封`，**到此为止，不谈流**；
   - 账号状态读不到 → `⚠️ 无法读取账号状态，未能确认是否已解封`，**不报流数结论**；
   - 账号确实已解封 + 无任何流 → `✅ 账号已解封，该用户当前没有任何播放流（原有 N 个已断开，未重连）`；
   - 账号确实已解封 + 仍有流 → `⚠️ 账号已解封，但该用户仍有 N 个流在播放 —— 很可能是解封后重连，请手动处理`；
   - **取不到会话状态 → 明确写"未能确认"，绝不猜成"已停止"**。

**复验为什么按 `UserId` 而不是 session id**：会话 id 在客户端重连后会**变**，拿旧 id 去查永远查不到 → 永远报"已断开"。所以复验改用 `/emby/Sessions` 里该用户的 `UserId` + `NowPlayingItem` 过滤，重连与否都能看见。

**日志**里每个被拒绝的会话都会记一条 `WARNING`（含 session id、用户与错误原因）；每轮检测记一条 `INFO`（`同时播放限制: user=..., streams=..., warns=..., 停止指令已下发=..., 服务端拒绝=..., 临时禁用踢流=..., 封禁=...`），复验结果另记一条 `INFO`（`踢流复验: user=..., 结果=...`），便于管理员跟进。

> 📌 被服务端拒绝的流不会被计入下发数，**警告计数照常 +1**。
>
> 📌 复验是**后台任务**，不阻塞本轮检测；若 bot 在 60 秒内重启，这次复验会丢失（首报已经发出，不影响封禁判定）。但**还原不会丢** —— 启动自恢复会无条件还原所有 `kick_until`。

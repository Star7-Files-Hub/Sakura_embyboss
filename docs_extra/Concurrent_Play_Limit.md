# 同时播放限制检测

## 功能概述

同时播放限制检测功能可以监控 Emby 服务器上所有用户的活跃播放会话，当某个用户的播放流数量超过**其适用的上限**（见下文「判定规则」）时，自动执行警告、终止所有流、群内通报，并在超过警告次数后自动封禁账号。

## 功能特性

- **播放限制**：设置每个用户允许的同时播放流数量（默认 2 个）
- **白名单独立上限**：白名单用户（`lv: a`）默认豁免，可在控制面板打开开关后单独设限（默认 4 个）
- **管理员永久豁免**：bot 管理员始终不受并发限制，硬编码、没有开关
- **自动终止**：超限后强制终止该用户的所有播放流
- **私信警告**：向违规用户发送私信警告
- **群内通报**：违规事件自动发送到配置的主群
- **累计警告**：记录每个用户的警告次数
- **自动封禁**：超过警告阈值后自动封禁账号
- **灵活配置**：所有限制参数均可通过控制面板调整

## 配置说明

在 `config.json` 中添加以下配置项：

```json
{
  "concurrent_play_limit_enabled": false,
  "concurrent_play_limit": 2,
  "concurrent_play_warn_threshold": 3,
  "concurrent_play_check_interval": 60,
  "concurrent_play_limit_whitelist_enabled": false,
  "concurrent_play_limit_whitelist": 4
}
```

| 配置项 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `concurrent_play_limit_enabled` | bool | `false` | 是否启用同时播放限制检测 |
| `concurrent_play_limit` | int | `2` | 每人允许的同时播放流数量 |
| `concurrent_play_warn_threshold` | int | `3` | 警告次数上限，超过自动封禁 |
| `concurrent_play_check_interval` | int | `60` | 检测间隔（秒），建议 30-300（面板最小 10） |
| `concurrent_play_limit_whitelist_enabled` | bool | `false` | 白名单用户是否也纳入并发限制；`false` = 白名单豁免 |
| `concurrent_play_limit_whitelist` | int | `4` | 白名单用户适用的上限，仅在上项为 `true` 时生效（面板输入范围 1-99） |

## 判定规则

检测到某个 Emby 账号的播放流数量后，先按 Emby UserId 到 bot 数据库里查用户记录（查不到的直接按第 2 条处理），再按下面的优先级判定（与代码实现一致，从高到低）：

1. **bot 管理员 → 永久豁免**：账号的 Telegram ID 在 bot 管理员列表里就一律跳过检查。这是**硬编码**的豁免，**没有开关**可以改，避免管理员把自己锁死；即使该账号同时还是白名单，也照样豁免。
2. **不在 bot 数据库里的 Emby 账号 → 跳过并记 warning**：例如直接建在 Emby 侧、bot 里没有记录的账号，既无法私信告警也无法封禁，因此会被跳过（日志里记一条 `WARNING`，含 Emby UserId 与 UserName）。**这类账号等于永久不受并发限制**，建议为其在 bot 中建档。
3. **白名单（`lv: a`）**：
   - `concurrent_play_limit_whitelist_enabled = false`（默认）→ 豁免，不做限制；
   - `= true` → 按 `concurrent_play_limit_whitelist`（默认 4）这个独立上限判定。
4. **其他用户** → 按 `concurrent_play_limit`（默认 2）判定。

判定用的是「该用户适用的上限」：播放流数量**严格大于**适用上限才会被终止 + 警告（正好等于上限不算超限）。群内通报和私信里显示的「限制: N 个」就是这名用户适用的上限（白名单用户显示的是白名单上限）。

> 📌 检测循环里会先用「可能生效的上限中较小的那个」做粗筛（开启白名单受限时即 `min(普通上限, 白名单上限)`），明显没超限的用户不查库就直接跳过；这只是性能优化，不会漏判。

**举例**（默认配置：普通上限 2、白名单上限 4、白名单受限关闭）：

| 账号类型 | 播 2 个流 | 播 3 个流 | 播 5 个流 |
|---|---|---|---|
| bot 管理员 | 不受限 | 不受限 | 不受限 |
| 白名单 `lv: a` | 不受限 | 不受限 | 不受限 |
| 普通用户 | 正常 | ⚠️ 终止 + 警告 | ⚠️ 终止 + 警告 |
| 不在 bot 数据库 | 不受限（仅记 warning） | 不受限（仅记 warning） | 不受限（仅记 warning） |

把「白名单是否受限」打开、白名单上限设为 4 之后，白名单账号播 5 个流同样会被终止 + 警告，播 2/3 个流仍然正常。

## 控制面板操作

在 bot 中输入 `/config` 打开控制面板，找到 **🎬 同时播放限制** 进入设置子面板。子面板顶部会显示当前状态、播放限制、白名单受限与白名单上限、警告阈值、检测间隔，并列出判定顺序。

### 设置选项

- **开关同时播放限制**：启用/禁用功能。按钮随状态显示 `❎ 同时播放限制`（未开启）、`✅ 同时播放限制`（已开启且定时任务在跑）或 `⚠️ 同时播放限制(未生效)`（开关已开但检测任务未注册，关闭再开启一次开关即可恢复）
- **设置播放限制数**：每人允许的同时播放流数量（默认 2，需输入大于 0 的整数）
- **白名单是否受限**：`❎`（默认）时白名单豁免；点成 `✅` 后白名单按白名单上限判定
- **设置白名单上限**：白名单用户允许的同时播放流数量（默认 4，面板接受 1-99）
- **设置警告阈值**：超过此次数将自动封禁
- **设置检测间隔**：检测周期（秒，面板最小 10，建议 30-300）
- **重置所有警告计数**：一键清零所有用户的警告记录

### 单个用户的警告调整

「重置所有警告计数」是整体操作。如果只是某个用户被误判、或者你想对他网开一面，用 `/kk` 单用户面板处理：

```
/kk [tg_id]        # 或对某人回复 /kk
```

面板里会多出一行 **`· ⚠️ 并发警告 | N / 阈值 次`**，以及独占一行的两个按钮：

- **➖ 警告-1**：把该用户的警告计数减 1。已经是 0 时不会变成负数，只提示「当前警告数已经是 0，无需再减」
- **🔄 重置警告**：把该用户的警告计数清零

两个操作都只改数据库里的 `concurrent_warn_count` 一个字段 —— **不会解除封禁、不会改动 Emby 策略、不会影响其他用户**。点完后面板会立即重渲染，计数当场更新。

> 面板刷新不会静默失败：
>
> 1. 重渲染用的是「刚写入的那个值」，而不是再查一次库 —— 渲染结果与写入动作严格对应。
> 2. 面板文本只反映**上一次渲染时**的计数。并发检测在别处把计数 +1 时，已打开的面板
>    就会停在旧值；这时管理员点「➖ 警告-1」，写回的值可能正好等于面板上已经显示的值，
>    Telegram 会以 `MESSAGE_NOT_MODIFIED` 拒掉编辑 —— 看起来就是「操作成功了但数字没动」。
>    因此并发检测写完计数后会立刻回调 `sync_kk_panel()` 把已打开的面板刷成最新值。
> 3. 同一个「管理员 + 被查看用户」只保留最新一条面板：发新面板前会删掉上一条，
>    避免管理员对着一条陈旧面板操作。
> 4. 万一消息真的编辑不了（例如被删除），会自动改发一条新面板并删掉旧的；
>    连改发都失败时会给管理员弹一个 `show_alert` 告警，而不是让他以为一切正常。
> 5. 编辑被限流（`FloodWait`）会自动等待重试，重试期间不会误发新面板。
>
> 具体错误码、消息 id、会话 id 都会写进日志。底层 `editMessage()` 里原先
> **完全静默**的三条 `BadRequest` 分支（`BUTTON_URL_INVALID` /
> `MESSAGE_NOT_MODIFIED` / `MESSAGE_ID_INVALID`）现在也会记日志，全仓 200+
> 处调用一并受益。
>
> 计数读不出来时面板显示「读取失败」而不是 `0` —— 读失败和真实的 0 必须区分开，
> 否则管理员会以为这个人没问题。用自解释文案而不是 `?`，是因为这一行普通用户
> 在 `/myinfo` 里也会看到。

未注册 Emby 账户的 TG 用户不显示这两个按钮（没有计数可调）。

> 注意：如果用户已经因为警告超阈值被封禁，调整警告数**不会自动解封**。解封请用同一个 `/kk` 面板上的「🌟 解除禁用」。

### 操作示例

```
/config → 🎬 同时播放限制
```

```
/kk 123456789 → ➖ 警告-1      # 给某个用户减一次警告
/kk 123456789 → 🔄 重置警告     # 把某个用户的警告清零
```

## 工作流程

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 定时检测（按设定间隔）                                      │
│    ↓                                                        │
│ 2. 获取 /emby/Sessions，按 UserId 分组                        │
│    ↓                                                        │
│ 3. 检查每个用户的播放流数量                                     │
│    ↓                                                        │
│ 4. 是否超过限制？                                              │
│    ├── 否 → 跳过                                              │
│    └── 是 → 继续                                              │
│         ↓                                                   │
│ 5. 终止该用户所有播放流（发送消息 + Playing/Stop）               │
│    ↓                                                        │
│ 5b. 等待 30 秒后**复验**，把实测断开数量补发到群里               │
│    ↓                                                        │
│ 6. 向用户发送私信警告                                          │
│    ↓                                                        │
│ 7. 在群内发送违规通报                                          │
│    ↓                                                        │
│ 8. 警告计数 +1                                                │
│    ↓                                                        │
│ 9. 警告次数 ≥ 阈值？                                           │
│    ├── 否 → 结束                                              │
│    └── 是 → 封禁用户（禁用 Emby 账号）                          │
└─────────────────────────────────────────────────────────────┘
```

图中的「是否超过限制」指该用户**适用的上限**：bot 管理员、以及默认配置下的白名单用户，在第 3 步就会被跳过；不在 bot 数据库里的账号也会被跳过并记 warning。详见上文「判定规则」。

## 群内通报格式示例

```
⚠️ 同时播放限制警告

用户: testuser (TG: 123456789)
Emby ID: abc123def456
当前播放流: 3 个 (限制: 2 个)
检测时间: 2024-01-15 14:30:25
累计警告: 2 / 3 次

  1. 🎬 电影A | 📱 Chrome
  2. 🎬 电影B | 📱 iPhone
  3. 🎬 剧集C | 📱 Android TV

✅ 已下发停止指令: 3 个流
🔎 终止复验结果将在 30 秒后补发（客户端断流通常有 20~30 秒延迟，此刻流可能还在播）

⚠️ 再犯 1 次将自动封禁账号！
```

30 秒后 bot 会再发一条**复验**通报，内容是实测结果：

```
🔎 终止复验
用户: testuser
✅ 已确认全部断开: 3/3 个流。
```

若仍有流没断，则改为：

```
🔎 终止复验
用户: testuser
✅ 已断开: 2 个 | ⚠️ 30 秒后仍在播放: 1 个
请手动处理仍在播放的会话。
```

## 用户私信格式

```
🚫 播放限制警告

您的账号当前有 3 个播放流，超出限制 2 个。
已向你的播放设备下发停止指令（客户端通常需要 20~30 秒才会真正断开）。
警告次数: 2 / 3

⚠️ 超过 3 次将自动封禁账号！
```

## 数据库说明

警告计数存储在 `emby` 表的 `concurrent_warn_count` 字段中。当用户被警告时自动递增，封禁后不会自动清零。

手动调整有两种粒度：

| 方式 | 作用范围 | 入口 |
|---|---|---|
| 重置所有警告计数 | 全部用户 | `/config` → 🎬 同时播放限制 |
| ➖ 警告-1 / 🔄 重置警告 | 单个用户 | `/kk [tg_id]` |

单用户调整只写这一个字段，不涉及封禁状态与 Emby 策略。

## 注意事项

1. **白名单默认豁免，但可以改成受限**：白名单用户（`lv: a`）默认不受并发限制；若希望白名单也守规矩，在控制面板打开「白名单是否受限」，再设置白名单上限（默认 4）。**bot 管理员是永久豁免的**，与这个开关无关。
2. **不在 bot 数据库里的 Emby 账号不受限**：这类账号（例如直接建在 Emby 侧）会被跳过并记一条 `WARNING`，既不会被告警也不会被封禁，建议为其在 bot 中建档以便统一管理。
3. **检测间隔不宜过短**：建议不低于 30 秒，避免对 Emby 服务器造成压力（面板最小 10 秒）
4. **与 Emby 原生限制的区别**：Emby 的 `SimultaneousStreamLimit` 策略会在播放开始时拒绝多余流，而本功能是在流已经开始后终止并警告，更适合需要"先播放后警告"的场景
5. **终止流的生效有延迟，且与是否支持远程控制无关**：`Playing/Stop` 返回 204 只代表**服务端接受了指令**，客户端真正断流通常还要 **20~30 秒**（2026-10-04 在 Emby 4.10 上实测 23.9s / 26.7s）。该字段 `SupportsRemoteControl` 在这台服务器上 2599 个会话**全部为 False**，但停止指令依然生效，所以它**不是**终止失败的原因，不要据此判断。

## 终止结果的处理（已下发 ≠ 已停止）

终止流依赖 Emby 直连的 `POST /emby/Sessions/{id}/Playing/Stop`。由于「服务端接受」与「客户端真的断流」之间有 20~30 秒延迟，本功能**不会在当场就宣称"已终止"**，而是分两步如实告知：

1. **首报（立刻）**：只说已下发的数量
   - `✅ 已下发停止指令: N 个流`；
   - 有被服务端拒绝的，追加 ` | ❌ 服务端拒绝: N 个流`；
   - 并提示 `🔎 终止复验结果将在 30 秒后补发`。
2. **复验（30 秒后）**：重新拉 `/emby/Sessions`，用**实测**结果补发一条群通报
   - 全部断开 → `✅ 已确认全部断开: N/N 个流。`
   - 仍有流在播 → `✅ 已断开: X 个 | ⚠️ 30 秒后仍在播放: Y 个`，并提示手动处理；
   - **取不到会话状态 → 明确写"未能确认"，绝不猜成"已停止"**。

**用户私信**的文案同样按实际下发结果变化：

- 全部下发成功 → "已向你的播放设备下发停止指令（客户端通常需要 20~30 秒才会真正断开）。"；
- 全部被拒 → "⚠️ 播放流停止指令**未能下发**，请**立即手动停止播放**，否则将直接封禁账号。"；
- 部分被拒 → "已下发 X 个流的停止指令，另有 Y 个流服务端拒绝，请**立即手动停止播放**，否则将直接封禁账号。"。

**日志**里每个被拒绝的会话都会记一条 `WARNING`（含 session id、用户与错误原因），复验结果另记一条 `INFO`（`终止复验: user=..., 已断开=..., 仍在播放=...`），便于管理员跟进。

> 📌 被服务端拒绝的流不会被计入下发数，**警告计数照常 +1**。本功能只有 Emby 直连这一条终止通道，没有备选通道：没能终止掉的流需要用户自行停止或管理员手动处理。
>
> 📌 复验是**后台任务**，不阻塞本轮检测；若 bot 在 30 秒内重启，这次复验会丢失（首报已经发出，不影响封禁判定）。
